# Item 15: the mini scenario set, run bare on both sides

2026-09-07. Approved shape: `ROADMAP.md` item 15. The suite:
`scripts/loop_live.py` (commit 4ecb46e). Full output of the first run:
`reports/2026-09-07_mini_set_both_run1.txt`.

## 1. The set

Eight scenarios, one per capability, each checked on harness events and the
store, never on the model's wording (the request text is literal):

| | capability | the checks |
|---|---|---|
| A | a plain question | one model call, no tool, an answer |
| B | one tool | `read_file` ran, no failure, the result reached the model, the answer uses it |
| C | files and a command | `write_file` and `run_command`, the file exists, `exit code: 0` in the result, the output in the answer |
| F | the browser | `write_file` and `inspect_page`, the file exists, no failure, a `[ref=e…]` read, an answer |
| W | the web | `fetch_page` or `view_web_page`, no failure, "Example Domain" reached the model, and is in the answer |
| H | memory and history | `remember_fact` in one conversation, the fact in the answer of another; the exact error text behind a summary read via `search_history`/`read_history`, nothing rewritten |
| E | a failing tool | `edit_file` ran, `fs.ambiguous_edit` reached the loop, the model answered, not ended by the repeat guard, `tool_failed` carries code and message |
| M | control | a message offered once the first tool was asked for is taken (`turn_interjected`), stored where it was read, answered ("144"), the three files still written; a stop during a second turn ends it with the stop message and fewer than five files |

Both profiles run bare: the workspace (so any `AGENTS.md`) and the
scenario's conversations are cleared first, locally in a temporary
directory, deployed in the probe user's directory on the Volume. Modes:
local (default), `--deployed`, `--both` with a side-by-side table. The wider
letters (G I J K O P Q R S) stay available for item 19.

Acceptance: every check of every scenario passes in one deployed run.

**All 16 passed; the set is accepted deployed.** What the two sides show:

- **No difference in what the model did.** Same tools in the same order on
  every scenario but H, where deployed the model called `search_history`
  and then `read_history` (one more call, +16 s) and locally
  `search_history` alone. Token counts differ by ~300 per turn: the
  capability list names the deployed runner and renderer.
- **The environment's seconds:** deployed is slower on B, W, E (+3 to +6 s:
  the Volume reload and commit around the turn, the Postgres store) and
  faster on F (−10 s: the renderer is beside the worker there; locally it
  starts Chromium). C is equal: the command's own run dominates.
- **M, the item 20 mechanism under the suite:** on both sides the message
  was taken after the first batch, answered with 144, and the three files
  were still written and read back — the persistence rule added today held
  (ISS-0059 not seen). The stop ended the second turn after three tool
  calls with "Stopped at your request."
- **Unasked:** C called `send_file` on both sides after running the script,
  which the request did not ask for; harmless, noted for the tool review
  (item 16).
- **Cost:** telemetry keeps tokens, not money; the table has no dollar
  column. A price column needs the provider's own `usage.cost`, which the
  dumps carry and the trace does not (item 18).

## 3. What the mini set does not check

Agentic quality (whether the model looked before writing, how it recovered)
and the wider shapes: a restart mid-turn, a fold mid-turn, a PDF, a timeout,
a chart, a repair. Those are item 19, with an LLM judge where a harness
fact cannot decide.
